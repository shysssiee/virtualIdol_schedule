# v1.2 r7 安裝與使用教學

## 更新現有 r6 網站
1. 備份 Supabase 資料與目前 GitHub 檔案，保留自己的 docs/config.js。請協作者先儲存內容、暫停編輯。
2. Supabase → SQL Editor → New query，貼上 database/upgrade-v1.2-r7.sql 全文，按 Run。它保留既有帳號與行程，也保留舊修正回報並將其納入留言板；可重複執行。既有網站不要重跑 schema.sql。
3. 將完整 docs 覆蓋至 GitHub 原本發布資料夾，放回自己的 config.js。等 Pages 部署完成，確認版本 v1.2 r7、舊行程正常。
4. 協作者重新整理後登入，按「協作後台」。站主仍按「站主管理」。

## 後台使用
- 協作者：行程管理、成員與紀念日、協作者名單、建議／問題留言板、我的帳號。僅修改自己的行程；他人行程可回報。成員僅新增；個人紀念日沿用原本權限。
- 協作者名單只顯示目前啟用帳號的暱稱、身分與在線狀態，不回傳 Email／UUID。每30秒更新，斷線最晚約95秒後轉離線。
- 留言板：填標題和問題／建議內容，所有登入且啟用的協作者都能查看。作者可修改自己的文章，站主可修改全部；僅站主可刪除。
- 站主點留言後填「站主回答」，完成工作才勾選「已處理」並儲存；也可取消勾選改回未處理。回答與狀態分開。
- 列表可篩選已處理／未處理。發文後按重新整理更新列表。行程的回報站主會附上行程連結。

## 分享標題自動部署：只設定一次（選用）
普通網站更新完成後，再設定這一段；不設定也可繼續用網站及原本的標題下載功能。

1. GitHub 專案根目錄上傳 scripts/sync-share-title.mjs，以及 .github/workflows/pages.yml。不要放到 docs 裡面。
2. 本範本使用 main 分支與 docs 資料夾。若你的預設分支是 master，修改 pages.yml 的 branches 為 [master]，並將工作流程上傳預設分支。
3. GitHub → Settings → Secrets and variables → Actions → New repository secret，新增兩項：
   - SUPABASE_URL：自己的 Supabase 專案 URL（和 config.js 相同）。
   - SUPABASE_PUBLISHABLE_KEY：自己的 publishable／anon key（和 config.js 相同）。不要使用 service_role 或 secret key。
4. Settings → Pages → Build and deployment → Source 改為 GitHub Actions。若已有另一份 Pages 部署 workflow，停用那份部署工作流程，避免互相覆蓋；保留其他檢查流程。
5. Actions → Calendar Pages → Run workflow → 選預設分支 → Run workflow。等綠色成功再確認網站。失敗時查看 Synchronize share title／Deploy 步驟，先確認 secrets、分支及 Pages Source。
6. 往後後台儲存站名，瀏覽器立即使用新站名；分享用靜態標題在下一次部署更新。每小時排程執行一次，也可隨時按 Run workflow；GitHub 排程可能延遲，社群舊快取仍可能保留。
7. 設定完成後不必再下載或替換 index.html；自動流程只改部署產物中的站名標題，不更動資料庫或原始檔，不清除行程。

公開儲存庫長時間沒有活動時，GitHub 可能停用排程；可在 Actions 重新啟用。若需「儲存後即時部署」，還要另接安全的後端觸發機制，本版採定時部署，並未宣稱即時強制刷新社群。

官方參考：https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages

# 安裝與升級 — v1.2 r4

## 本次 r4 更新
1. 保留原本的 docs/config.js，並先備份 Supabase 資料。
2. 已更新到 r3：在 SQL Editor 執行 database/upgrade-v1.2-r4.sql。此前未執行 r3 的網站，先執行 upgrade-v1.2-r3.sql，再執行 r4。
3. 將 docs 全部內容覆蓋至 GitHub Pages 發布資料夾，放回自己的 config.js。
4. 等部署完成，重新整理；頁尾應顯示 v1.2 r4。
5. 站主登入 → 站主管理 → 協作者管理，即可看到在線圓點。

在線狀態：頁面可見時每30秒回報一次，近95秒有回報顯示綠點；離線灰點。關閉頁面或網路中斷可能最多約95秒才轉為離線。橘點表示讀取失敗，請先確認 r4 SQL 已執行。不同分頁分別紀錄；公開訪客無法讀取帳號在線資料。

## r3 基礎更新（尚未安裝時）
1. 保留自己原本的 docs/config.js，並備份現有 Supabase 資料。
2. 在 Supabase 的 SQL Editor 貼上 database/upgrade-v1.2-r3.sql 全文，按 Run。本次新增紀念日與修正回報資料表及權限；不刪除既有行程，可重複執行。
3. 將此包 docs 的所有檔案及 vendor 子資料夾覆蓋至 GitHub 專案原本發布的資料夾。將保留的 config.js 放回。
4. 等待 GitHub Pages 部署完成，重新整理網站，頁尾應顯示 v1.2 r3。若仍是舊版，清除網站快取。
5. 站主登入後到「團體與共用分類」新增紀念日；「修正回報」查看協作者送來的修改內容。

不要只更新 app.js；extras.js、anniversaries.js、vendor 與 korean-holidays.json 都要上傳。

## 從 v1.1 升級
先執行 database/upgrade-v1.2.sql，再依序執行 database/upgrade-v1.2-r3.sql、database/upgrade-v1.2-r4.sql，然後更新 docs。

## 全新安裝
1. 在 Supabase 新建專案，SQL Editor 執行 database/schema.sql，接著執行 database/upgrade-v1.2-r3.sql 與 database/upgrade-v1.2-r4.sql。
2. 在 Authentication → Users 建立站主帳號，將 UUID 填入 database/create-owner.sql 的指定位置後執行。
3. 編輯 docs/config.js，填入專案 URL 與 publishable／anon key。不要把 service_role key 放入網頁。
4. 將專案上傳 GitHub；Settings → Pages 選擇要發布的分支與 /docs。其他部署資料夾請依實際設定放置網頁。
5. Supabase Authentication 的 Site URL 與 Redirect URLs 設為自己的 GitHub Pages 網址。
6. 協作者帳號在 Supabase 人工建立，網站站主管理填入 UUID 授權。

詳細的舊版帳號設定流程保留在「文件封存/v1.2/README.md」。

## 加入個人日曆
- Google：行程資訊內按「Google 日曆」，確認開始時間、設定通知、儲存。網站不會直接取得你的 Google 帳號權限。
- Apple／其他：按按鈕下載 .ics，包含開始時間與提前10分鐘的提醒。iPhone 是否直接匯入取決於使用的瀏覽器；若只預覽檔案，可將檔案透過 Apple Mail 開啟，或使用支援 .ics 匯入的日曆工具。
- 本次不是日曆訂閱，網站之後修改行程不會自動更新已加入的個人日曆。最後的提醒以手機日曆通知設定為準。

## 年曆範圍
內建韓國農曆支援至2050年；假日資料涵蓋2023～2050，由 date-holidays 3.37.0 產生。臨時假日、選舉日或未來制度變更需更新資料，不應視為官方保證。農曆日期由瀏覽器的 Chinese Calendar 計算。
第三方程式與假日資料的授權與來源附在 docs/vendor。

## 成員與登入更新（同為 r5）
- 行程的參與成員區可新增成員，立即勾選並加入團體共用清單；成員建立成功後，即使取消行程也會保留。
- 同團體名字忽略前後空白與英文大小寫，重複新增沿用原資料。修改、刪除與排序仍限站主。
- 生日未選成員時，用名字建立／沿用成員。個人出道／紀念日可先新增或選成員；全團紀念日不會建立假成員。
- 後台「團體與共用分類 → 成員」展開團體即可看成員及生日、出道與紀念日期；修改紀念日使用下方紀念日管理區。
- 問候使用目前顯示時區：05:00–11:59早安、12:00–17:59午安，其餘晚安。登入成功顯示歡迎視窗，重新整理不重複顯示。

全新安裝：依序執行 schema.sql、upgrade-v1.2-r3.sql、upgrade-v1.2-r4.sql、upgrade-v1.2-r5.sql，再建立站主。舊版升級請先完成對應 v1.2/r3/r4 升級，再執行 r5。
